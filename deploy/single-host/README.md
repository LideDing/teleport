# 单机部署手册（systemd + 本机 NGINX 分发 agent 二进制）

> 场景：单机部署，Teleport 控制面运行在一台 Linux 机器上。K8s 部署（控制面运行在 TKE）是另一个独立场景，见 `deploy/k8s/README.md`；两者的对比见 `deploy/README.md`。
> 适用版本：Teleport v18.11.1 OSS（AGPL）源码，分支 `docs/selfhosted-cos-cdn`，Linux amd64。
> 部署形态：一台机器同时运行 Teleport（auth + proxy + ssh，由 systemd 管理）和 NGINX。agent 安装、更新时从本机 NGINX 的 8443 端口下载自编译、自签名的二进制，不访问 `cdn.teleport.dev`。
> 文中的域名、IP、路径都是本机当前部署的实际值（见附录），换机器时替换即可。
> 同一场景改用腾讯云 COS 分发，或者接入 K8s 集群、Web App，见同目录的 `QUICKSTART_COS.md`；下载地址和签名机制的原理见仓库根目录的 `SELF_HOSTED_COS_CDN.md`。

## 部署流程速览

| 步骤 | 内容 | 章节 |
| --- | --- | --- |
| 1 | 编译二进制，生成签名密钥，重编带公钥的 teleport-update，打包并签名 | 第 3 节 |
| 2 | 安装 NGINX，在 8443 端口发布产物 | 第 4 节 |
| 3 | 安装 Teleport、写配置、设置下载地址、用 systemd 启动 | 第 5 节 |
| 4 | 创建超级管理员 | 第 6 节 |
| 5 | 验证服务和下载链路 | 第 7 节 |
| 6 | 接入 agent | 第 8 节 |

## 1. 架构与端口

```text
agent 机器                              本机 teleport.devcloud.oitcep.com
安装脚本、agent 连接集群    ──443──▶    Teleport（auth + proxy + ssh）
teleport-update 下载二进制  ──8443─▶    NGINX（/var/www/teleport-cdn）
```

下载链路：

1. Proxy 进程从 `/etc/default/teleport` 读取环境变量 `TELEPORT_CDN_BASE_URL`，写进它生成的 agent 安装脚本。
2. agent 上的 `teleport-update` 从这个地址下载 `teleport-v<版本>-linux-<arch>-bin.tar.gz` 和同名的 `.sha256`、`.sig`，校验哈希，并用编译时内置的公钥验证签名。
3. 所以要做三件事：编出内置自己公钥的 `teleport-update`；把签好名的包放进 NGINX；让 Proxy 指向 NGINX。

> **服务端必须用本分支编译。** 原版在集群没有配置 agent 托管更新（没有 `autoupdate_agent_rollout`）时会下发旧版安装脚本，它无视 `TELEPORT_CDN_BASE_URL`，直接从 `cdn.teleport.dev` 或官方 apt/yum 源安装官方二进制。本分支的提交 `6f6cf8ce532`（`lib/web/scripts.go`）让 AGPL 构建始终下发 teleport-update 版脚本。

| 端口 | 进程 | 用途 | 对外开放 |
| --- | --- | --- | --- |
| 443 | teleport | Web UI、tsh/tctl、agent 注册和反向隧道（multiplex 模式下全部复用 443） | 是 |
| 8443 | nginx | agent 二进制下载 | 是（至少对 agent 机器开放） |
| 3025 | teleport | Auth 服务，供本机 tctl 使用 | 否 |
| 3022 | teleport | 本机自身作为 SSH 节点 | 否 |

## 2. 前置条件

- 系统：TencentOS Server 4，root 用户。
- DNS：`teleport.devcloud.oitcep.com` 和 `*.teleport.devcloud.oitcep.com` 都解析到本机（通配记录供 App Access 使用）。
- 证书：已用 certbot 签发主域名 + 通配符证书（ECDSA，DNS-01，certbot-tcc 插件），位于 `/etc/letsencrypt/live/teleport.devcloud.oitcep.com/`。Teleport 和 NGINX 共用这一张证书。
- 网络：agent 机器能访问本机的 443 和 8443。云上安全组需要放行；本机 firewalld 未启用。
- agent 机器：有 systemd 和 curl，glibc ≥ 2.38（本机编出的 `teleport` 依赖 `GLIBC_2.38`），例如 TencentOS 4、Ubuntu 24.04。
- 编译环境：见 3.1。

## 3. 编译

本节命令都在仓库根目录以 root 执行：

```bash
cd /root/github.com/teleport
```

### 3.1 构建环境（一次性，本机已具备）

- **Go**：不用手动安装 1.25.14，`GOTOOLCHAIN=go1.25.14` 会自动下载。本机 `/usr/local/go` 是 1.26.7，**不指定 `GOTOOLCHAIN` 就会用 1.26.7 编译**，与仓库要求的版本不一致。
- **静态 libelf**：`sessionhelper` 等目标用 `-Wl,-Bstatic -lelf` 静态链接，发行版只提供 `libelf.so`，会报 `cannot find -lelf`。按官方配方（`build.assets/buildbox/thirdparty-libs.mk` 的 libelf 段）编译安装：

  ```bash
  git clone https://github.com/arachsys/libelf /tmp/libelf
  cd /tmp/libelf
  git checkout b80c36da9d70158f9a38cfb9af9bb58a323a5796    # v0.191
  make CFLAGS+=-fPIE libelf.a
  make install-headers install-static PREFIX=/usr/local   # 安装到 /usr/local/lib/libelf.a
  ```

- **其他**：gcc、clang（编译 BPF）、Rust（fdpass-teleport、RDP 解码器）、Node.js + pnpm（Web UI），以及 libbpf、zstd、zlib 静态库和 PAM 头文件。本机都已具备，新机器按 `make` 的报错补装。

### 3.2 编译全部二进制

```bash
# 可选：让 teleport version 显示当前提交（gitref.go 只在 Makefile 变化时才会重新生成）
printf '// Code generated by "make version". DO NOT EDIT.\n\npackage teleport\n\nfunc init() { Gitref = "%s" }\n' \
  "$(git describe --long --tags)" | gofmt > gitref.go

GOTOOLCHAIN=go1.25.14 make full TELEPORT_UPDATE_DEV_BUILD=1
./build/teleport version     # Teleport v18.11.1 git:v18.11.1-... go1.25.14
```

- 产物在 `build/`：`teleport`、`tctl`、`tsh`、`tbot`、`fdpass-teleport`、`teleport-update`。
- `TELEPORT_UPDATE_DEV_BUILD=1` 只是让 make 跳过公钥检查。这一步编出的 `teleport-update` 没有公钥，3.4 要重编。
- 编译日志开头有大量 `/bin/bash: - : invalid option`，是 Makefile 解析阶段的无害噪音，不影响产物。

### 3.3 生成签名密钥（一次性）

```bash
./sign-teleport-artifacts.sh --keygen-only
# 想给私钥加密码：TELEPORT_SIGN_PASS='你的密码' ./sign-teleport-artifacts.sh --keygen-only
# 加了密码的话，之后每次签名也要带上同样的 TELEPORT_SIGN_PASS
```

在仓库根目录生成三个文件（都已加入 `.gitignore`）：

| 文件 | 用途 |
| --- | --- |
| `teleport-signing.key` | ECDSA P-256 私钥（权限 0600），用来签名，务必离线备份 |
| `teleport-signing.pub` | PEM 公钥，用来自检 |
| `teleport-signing.pub.b64` | 公钥的 base64，编译 `teleport-update` 时注入 |

私钥已存在时脚本会拒绝覆盖。**不要随意更换密钥**：已安装的 agent 内置的是旧公钥，换钥后它们验证不了新签名的包，更新会失败。

### 3.4 重编 teleport-update（注入公钥）

```bash
KEY=$(cat teleport-signing.pub.b64)
GOTOOLCHAIN=go1.25.14 GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -buildvcs=false \
  -ldflags "-w -s -X main.artifactSignaturePublicKeyB64=$KEY -X main.artifactSignatureBackupPublicKeyB64=$KEY" \
  -o build/teleport-update ./tool/teleport-update

./build/teleport-update status
# 报 "Teleport is not installed by teleport-update with this suffix." 是正常的；
# 报 "artifact signature public key is not configured" 说明公钥没注入成功
```

Makefile 只在 `GITHUB_REPOSITORY_OWNER=gravitational` 时注入公钥，而设置这个变量会把所有二进制变成 Community 版构建，所以这里直接用 `go build`。

### 3.5 打包并签名

```bash
make build-archive
./sign-teleport-artifacts.sh build/artifacts/teleport-v18.11.1-linux-amd64-bin.tar.gz
```

- 打包产物是 `build/artifacts/teleport-v18.11.1-linux-amd64-bin.tar.gz`，包内顶层目录为 `teleport/`。同目录还有一份内容相同的 `-centos7-bin.tar.gz` 副本，不需要发布。
- 签名脚本生成 `.sha256` 和单行 base64 的 `.sig`（ECDSA-SHA256，ASN.1 DER 编码），并立即用公钥自检。
- **顺序不能乱**：先重编 teleport-update（3.4），再打包，最后签名。重新打包后旧签名就作废了，必须重签。

## 4. 搭建 NGINX 文件服务器（8443）

### 4.1 安装与配置

```bash
dnf install -y nginx
mkdir -p /var/www/teleport-cdn

cat > /etc/nginx/conf.d/teleport-cdn.conf <<'EOF'
# Teleport agent 二进制分发站点，Proxy 通过 TELEPORT_CDN_BASE_URL 指向这里
server {
    listen 8443 ssl default_server;
    listen [::]:8443 ssl default_server;
    http2 on;
    server_name teleport.devcloud.oitcep.com;

    # 与 Teleport 共用 certbot 证书
    ssl_certificate     /etc/letsencrypt/live/teleport.devcloud.oitcep.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/teleport.devcloud.oitcep.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:TeleportCDN:1m;

    root /var/www/teleport-cdn;
    autoindex off;

    location / {
        limit_except GET { deny all; }   # 只读：仅允许 GET/HEAD
        try_files $uri =404;
    }
}
EOF

nginx -t && systemctl enable --now nginx
```

- 必须用 HTTPS 和受信任的证书：`teleport-update` 拒绝 http 地址，下载时也会校验证书。
- 下载目录放在 `/var/www` 下：NGINX 的 worker 进程以 `nginx` 用户运行，读不了 `/root` 下的文件。
- 证书私钥由 NGINX 主进程（root）读取，不需要修改 `/etc/letsencrypt` 的权限。
- 可选：发行版自带的 `/etc/nginx/nginx.conf` 里有一个 `listen 80` 的默认站点，用不上可以删掉这个 `server` 块（本机已删，原文件备份为 `/etc/nginx/nginx.conf.orig`）。

### 4.2 发布产物

```bash
cd /root/github.com/teleport
install -m 644 build/artifacts/teleport-v18.11.1-linux-amd64-bin.tar.gz{,.sha256,.sig} /var/www/teleport-cdn/
```

下载目录是平铺的，三个文件直接放在根下：

```text
/var/www/teleport-cdn/
├── teleport-v18.11.1-linux-amd64-bin.tar.gz
├── teleport-v18.11.1-linux-amd64-bin.tar.gz.sha256
└── teleport-v18.11.1-linux-amd64-bin.tar.gz.sig
```

- 文件名固定为 `teleport-v<版本>-linux-<arch>-bin.tar.gz`（见 `lib/autoupdate/package_url.go`），版本带 `v` 前缀，arch 为 `amd64`、`arm64` 等。
- 没有配置托管更新时，agent 安装的是 Proxy 自己的版本，所以 **Proxy 当前版本的三个文件必须在**。有 ARM 机器的话，还要另外构建 arm64 产物（本手册只覆盖 amd64）。

从 8443 端口自检下载和签名：

```bash
B=https://teleport.devcloud.oitcep.com:8443/teleport-v18.11.1-linux-amd64-bin.tar.gz
curl -fsS "$B" -o /tmp/t.tgz
curl -fsS "$B.sha256"; sha256sum /tmp/t.tgz        # 两个哈希应一致
curl -fsS "$B.sig" | base64 -d > /tmp/t.sig
openssl dgst -sha256 -verify teleport-signing.pub -signature /tmp/t.sig /tmp/t.tgz   # 输出 Verified OK
rm -f /tmp/t.tgz /tmp/t.sig
```

### 4.3 证书续期后自动重载 NGINX

```bash
cat > /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh <<'EOF'
#!/bin/sh
# certbot 续期成功后让 nginx 加载新证书（Teleport 按 https_keypairs_reload_interval 自行重新加载）
systemctl try-reload-or-restart nginx
EOF
chmod 755 /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
```

续期本身目前还没有自动化，见 9.4。

## 5. 部署 Teleport 服务

### 5.1 安装二进制

```bash
cd /root/github.com/teleport
for b in teleport tctl tsh tbot fdpass-teleport teleport-update; do
  install -m 755 build/$b /usr/local/bin/$b
done
teleport version
```

服务端已经在运行时，按 9.2 升级（先备份）。

### 5.2 配置文件

```bash
cat > /etc/teleport.yaml <<'EOF'
version: v3
teleport:
  nodename: teleport.devcloud.oitcep.com
  data_dir: /var/lib/teleport
  advertise_ip: 21.214.36.27              # 本机 IP，换机器要改
  log:
    output: /var/log/teleport.log
    severity: INFO
    format:
      output: text
auth_service:
  enabled: "yes"
  listen_addr: 0.0.0.0:3025
  cluster_name: teleport.devcloud.oitcep.com
  proxy_listener_mode: multiplex          # 所有协议复用 443
  proxy_protocol: "off"
ssh_service:
  enabled: "yes"
proxy_service:
  enabled: "yes"
  web_listen_addr: 0.0.0.0:443
  public_addr: teleport.devcloud.oitcep.com:443
  proxy_protocol: "off"                   # 前面没有四层负载均衡，不接受 PROXY 协议头
  https_keypairs:
  - key_file: /etc/letsencrypt/live/teleport.devcloud.oitcep.com/privkey.pem
    cert_file: /etc/letsencrypt/live/teleport.devcloud.oitcep.com/fullchain.pem
  https_keypairs_reload_interval: 1h      # 证书续期后 1 小时内自动加载
EOF
chmod 600 /etc/teleport.yaml
teleport configure --test /etc/teleport.yaml    # 输出 OK /etc/teleport.yaml
```

> `cluster_name` 在首次启动时写入数据目录，之后不能修改。换域名时要先停服务，把旧的 `/var/lib/teleport` 移走（不要删除，留作备份），再用新配置启动。

### 5.3 配置 agent 下载地址

```bash
cat > /etc/default/teleport <<'EOF'
# agent 安装、更新时下载 Teleport 二进制的地址（https://，不带结尾斜杠）
TELEPORT_CDN_BASE_URL=https://teleport.devcloud.oitcep.com:8443
EOF
```

这是 Proxy 进程的环境变量：AGPL 构建没有设置它时会拒绝生成安装脚本；修改后要重启 Teleport 才生效。

### 5.4 启动服务

```bash
cd /root/github.com/teleport
cp examples/systemd/teleport.service /etc/systemd/system/teleport.service   # 已包含 EnvironmentFile=-/etc/default/teleport
systemctl daemon-reload
systemctl enable --now teleport
systemctl status teleport --no-pager

# 确认进程拿到了下载地址
tr '\0' '\n' < /proc/$(systemctl show -p MainPID --value teleport)/environ | grep TELEPORT_CDN_BASE_URL
```

## 6. 创建超级管理员

### 6.1 创建角色和用户

```bash
cd /root/github.com/teleport
tctl create -f deploy/single-host/rbac-super-admin.yaml   # 创建或覆盖 super-admin 角色
tctl users add lideding --roles=super-admin,editor,access,auditor --logins=root
```

`tctl users add` 会输出一个邀请链接，1 小时内有效。用户打开链接设置密码并绑定 OTP（集群默认 `second_factor: otp`）。

| 操作 | 命令 |
| --- | --- |
| 邀请链接过期后重新生成 | `tctl users reset lideding` |
| 给已有用户授权（会覆盖原有角色） | `tctl users update <用户名> --set-roles=super-admin,editor,access,auditor` |
| 查看用户 | `tctl users ls`、`tctl get user/lideding` |

### 6.2 权限说明

`super-admin` 角色定义在 `deploy/single-host/rbac-super-admin.yaml`：

| 范围 | 授权 |
| --- | --- |
| Teleport 管理 | 对所有资源的所有操作（用户、角色、token、集群配置等）；可模拟任意用户和角色（`impersonate`） |
| 服务器 | 所有节点，以 `root` 登录 |
| Kubernetes | 所有集群，组 `system:masters`（即 cluster-admin），所有资源 |
| 数据库 | 所有数据库，任意数据库用户（`db_users: "*"`）、任意库（`db_names: "*"`） |
| 其他 | 所有 Web 应用；Windows 桌面以 `Administrator` 登录；AWS/Azure/GCP 角色按通配 ARN 授权 |

- 同时分配预置角色 `editor`、`access`、`auditor`：Teleport 每个版本都会自动更新预置角色，能覆盖新功能；它们没有 deny 规则，叠加只会增加权限。
- SSH 登录名和 Windows 登录名都按字符串精确匹配，写 `"*"` 并不代表任意账号，所以角色里显式写了 `root` 和 `Administrator`。
- K8s 和数据库的权限在接入后才生效：K8s agent 需要有 impersonate 权限（官方 `teleport-kube-agent` chart 默认会配）；数据库里要真的有对应的用户，并配置成信任 Teleport 签发的证书。

### 6.3 验证权限（不签发凭据）

```bash
ID=$(tctl get nodes --format=json | python3 -c 'import json,sys; print(next(n["metadata"]["name"] for n in json.load(sys.stdin) if n["spec"]["hostname"]=="teleport.devcloud.oitcep.com"))')
tctl decision evaluate-ssh-access --username lideding --login root --server-id "$ID"
```

输出 JSON 里有 `"permit"` 表示允许，有 `"denial"` 表示拒绝。这是实验性的隐藏命令（第一行会打印 WARNING），只做模拟计算，不会给用户签发凭据。

## 8. 接入 agent

### 8.1 生成 token 并安装

在本机生成 token 和安装命令：

```bash
TOKEN=$(tctl tokens add --type=node --ttl=1h --format=text)
echo "curl -fsSL https://teleport.devcloud.oitcep.com/scripts/$TOKEN/install-node.sh | sudo bash"
```

在 agent 机器上执行打印出来的命令。也可以在 Web UI 的 Enroll New Resource → Linux Server 里生成同样的命令。

要给节点打标签，需要用 YAML 创建带 `spec.suggested_labels` 的 token。`tctl tokens add --labels` 只给 token 本身打标签，不会进入安装脚本。

```bash
TOKEN=$(openssl rand -hex 16)      # 安装脚本要求 token 是 32 位十六进制
tctl create <<EOF
kind: token
version: v2
metadata:
  name: $TOKEN
  expires: $(date -u -d '+1 hour' +%Y-%m-%dT%H:%M:%SZ)
spec:
  roles: [Node]
  join_method: token
  suggested_labels:
    env: [prod]
    team: [ops]
EOF
echo "curl -fsSL https://teleport.devcloud.oitcep.com/scripts/$TOKEN/install-node.sh | sudo bash"
```

### 8.2 安装过程

1. `install-node.sh` 向 Proxy 请求 `/scripts/install.sh`（teleport-update 版）。
2. 安装脚本从 8443 下载 tarball，取出其中的 `teleport-update`，执行 `teleport-update enable --proxy teleport.devcloud.oitcep.com:443 --base-url https://teleport.devcloud.oitcep.com:8443`。
3. `teleport-update` 再次下载 tarball，校验 `.sha256` 和 `.sig`，安装到 `/opt/teleport/default/versions/<版本>/`，并把 `teleport`、`tsh` 等链接到 `/usr/local/bin`。
4. 写入 `/etc/teleport.yaml`，启动 `teleport.service`，并创建 `teleport-update.timer`。

所以 NGINX 日志里一次安装对应 4 个请求：tarball 两次，`.sha256` 和 `.sig` 各一次。

### 8.3 检查

```bash
# 在 agent 上
systemctl status teleport --no-pager

# 在本机
tctl nodes ls
tail /var/log/nginx/access.log
```

### 9.2 发布新版本 / 升级

1. 更新代码后，按 3.2 → 3.4 → 3.5 编译、重编 teleport-update、打包并签名（版本号取自 `Makefile` 里的 `VERSION`）。
2. 按 4.2 把新版本的三个文件放进 `/var/www/teleport-cdn`。旧版本的文件保留，便于回滚。
3. 先备份，再升级服务端：

   ```bash
   cd /root/github.com/teleport
   TS=$(date +%Y%m%d%H%M%S)
   systemctl stop teleport
   cp -a /var/lib/teleport /var/lib/teleport.bak-$TS
   mkdir -p /usr/local/lib/teleport-bak-$TS
   for b in teleport tctl tsh tbot fdpass-teleport teleport-update; do
     cp -a /usr/local/bin/$b /usr/local/lib/teleport-bak-$TS/
     install -m 755 build/$b /usr/local/bin/$b
   done
   systemctl start teleport
   ```

4. 最后升级 agent（agent 的版本不能高于服务端，所以总是先升服务端）：
   - 新接入的 agent 会自动安装 Proxy 的新版本。
   - 已有的 agent 在没有配置托管更新时不会自动升级，在 agent 上执行 `sudo teleport-update update --now`。
   - 想让 agent 按时间窗自动升级，把 `deploy/single-host/autoupdate.yaml` 里的版本号改成新版本，再执行 `tctl create -f deploy/single-host/autoupdate.yaml`。

### 9.3 修改 agent 下载地址

1. 在新地址准备好同样的三个文件（必须是 https，证书受信任）。
2. 修改 `/etc/default/teleport` 里的 `TELEPORT_CDN_BASE_URL`，执行 `systemctl restart teleport`。这只影响之后新装的 agent。
3. 已装的 agent 把地址保存在各自的 `/opt/teleport/default/update.yaml`（`spec.base_url`）里，要在每台 agent 上执行：

   ```bash
   NEW_URL=https://downloads.example.com:8443   # 换成新地址
   sudo teleport-update enable --base-url "$NEW_URL"
   ```

### 9.4 证书续期

现状（2026-11-20）：

- 证书 2027-02-18 到期。Teleport 每小时重新读取证书，NGINX 由 4.3 的钩子在续期后重载，两边都不需要手动重启。
- **续期目前没有自动化**：系统的 `certbot-renew.timer` 没启用，而且系统的 `/usr/bin/certbot` 没有 tcc 插件。带插件的是 pyenv 里的 `/root/.pyenv/versions/3.12.16/bin/certbot`。
- `/etc/letsencrypt/renewal/teleport.devcloud.oitcep.com.conf` 里写的是 `certbot_tcc_credentials = credentials.ini`，是相对路径（签发时在 `/root/work/nginx-files-server/tls/` 下执行），在别的目录执行 renew 会找不到凭据。
- 凭据文件 `/root/work/nginx-files-server/tls/credentials.ini` 当前权限是 644，里面是云 API 密钥，应改为 600。

建议按下面的方式配置（尚未在本机执行）：

```bash

  /etc/letsencrypt/renewal/teleport.devcloud.oitcep.com.conf

# 演练：使用 Let's Encrypt 测试环境，会临时写入 DNS TXT 记录
```

## 10. 故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `install-node.sh` 输出 `An error has occurred. The token may be expired or invalid.`，Teleport 日志有 `Failed to get CDN base URL` | Proxy 进程没拿到 `TELEPORT_CDN_BASE_URL`（AGPL 构建没设置时拒绝生成脚本） | 检查 `/etc/default/teleport` 和 unit 的 `EnvironmentFile`，重启 Teleport |
| agent 从 `cdn.teleport.dev` 或官方 apt/yum 源下载 | 服务端不是用本分支编译的（缺 `6f6cf8ce532`），回退到了旧版安装脚本 | 用本分支重新编译并替换服务端二进制 |
| `teleport-update artifact signature public key is not configured` | `teleport-update` 编译时没注入公钥 | 按 3.4 重编，再重新打包、签名、发布 |
| `artifact signature verification failed for all trusted keys` | `.sig` 和 `teleport-update` 内置的公钥不配对，或重新打包后没有重签 | 用配对的私钥重新签名；确认 3.4 用的是同一个 `.pub.b64` |
| `signature not found: ...` 或 `checksum not found: ...` | NGINX 目录里缺 `.sig` 或 `.sha256` | 补齐三个文件 |
| `Teleport download not found: ...` 或 HTTP 404 | 文件名或版本不对（版本取 Proxy 当前版本，文件名带 `v`） | 按 4.2 的规则命名和放置 |
| `Teleport download base URL ... must use TLS (https://)` | 下载地址用了 http | 改成 https |
| agent 上报 `GLIBC_2.38 not found` | agent 系统的 glibc 太旧 | 换新系统，或用官方 centos7 buildbox 编译（glibc 2.17） |
| curl 报 `SSL: no alternative certificate subject name matches` | 访问的域名不在证书里（例如用 IP 访问） | 用证书里的域名访问 |
| `make full` 报 `cannot find -lelf` | 缺静态库 `libelf.a` | 按 3.1 编译安装 |
| `make build-archive` 报 `mkdir: cannot create directory ... File exists` | 仓库根目录有上次打包残留的 `teleport/` 目录 | 删掉这个目录后重试 |
| 编译日志开头大量 `/bin/bash: - : invalid option` | Makefile 解析阶段的噪音 | 无害，忽略 |
| tctl 报 `https private key does not exist: ...` | `teleport.yaml` 引用的证书文件不存在（例如换域名后没改路径） | 修正 `https_keypairs` 里的路径 |

## 11. 安全注意事项

- `teleport-signing.key` 是整套分发的信任根：权限 0600、不进 git（已在 `.gitignore` 中）、离线备份，可以用 `TELEPORT_SIGN_PASS` 加密。
- 不要随意更换签名密钥（见 3.3）。
- `super-admin` 相当于集群的 root，还能模拟任意用户，只授予确实需要的人；保持 OTP 二次验证开启。
- 邀请链接和 join token 都是凭据，不要发到公开渠道；用完或过期的 token 用 `tctl tokens ls`、`tctl tokens rm` 清理。
- NGINX 只读（仅 GET/HEAD）、不开目录列表，下载目录里只放发布产物。
- certbot 的云 API 凭据文件权限应为 600（见 9.4）。
